# Черновик карточки товара

Прототип для B2B-магазина приборов. На входе данные о товаре (JSON или веб-форма), на выходе черновик карточки: SEO-заголовок, описание, характеристики, поисковые запросы и блок для менеджера.

## Установка и запуск

Нужен Python 3.10 или новее.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
```

В `.env` впишите `LLM_API_KEY` от OpenRouter. Другой OpenAI-совместимый API подключается через `LLM_BASE_URL` и `LLM_MODEL`. Локальному серверу тоже нужен непустой ключ, подойдёт любой.

```bash
.venv/bin/python -m card_draft examples/input/testo-510.json   # результат в Markdown
.venv/bin/python -m card_draft examples/input/testo-510.json --format json
.venv/bin/uvicorn card_draft.web:app                           # веб-форма на http://127.0.0.1:8000
```

Тот же JSON принимает `POST /api/card`. Тесты к LLM не обращаются:

```bash
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest
```

## Промпт и решения

Системный промпт запрещает всё, чего нет во входных данных, в том числе общие знания о таком типе приборов. Указания внутри данных модель не выполняет. Если фактов мало, она пишет короткое описание, а если не указано назначение, в блоке для менеджера ставит «данных нет». Ответ приходит по JSON-схеме. Полный текст лежит в [prompts.py](card_draft/prompts.py).

Таблицу характеристик собирает код из входных данных, модель значения не пишет. Характеристики, которые покупатель обычно ожидает, модель только называет, а код добавляет их в таблицу с пометкой «данных нет».

Тексты сверяются с входными данными: числа, единицы измерения, обозначения вроде `Modbus` и `ГОСТ`, утверждения про гарантию, поверку, сертификаты. Проверяются и лимиты длины. Если что-то не сошлось, модель получает список проблем, всего до трёх попыток, после чего остаётся лучший черновик со статусом `needs_review`. Когда фактов не хватает на 800 символов, повторов нет: дотянуть можно только домыслами.

Клиент OpenAI-совместимый, поэтому модель меняется настройками. Локальную модель я не запускал: отвечать по JSON-схеме умеет не каждая.

## Ограничения

- Проверка сверяет значения, а не смысл. Вывод вроде «подходит для пищевых производств» она пропустит, поэтому результат остаётся черновиком для контент-менеджера.
- Известным считается любое число из входа, даже из названия модели или другой характеристики. Числа прописью не сверяются, списки единиц и утверждений фиксированные.
- Размер входа не ограничен, большой паспорт целиком уйдёт в платный запрос.
- Запросы синхронные, авторизации нет.

## Что можно улучшить

- Второй запрос к модели, который ищет утверждения без опоры на данные. Закроет проверку смысла, но запросов станет вдвое больше.
- Загрузка характеристик со страницы товара по ссылке из фида.
- Набор эталонных карточек для проверки изменений промпта и смены модели.
- Пакетная обработка каталога с отчётом, каким товарам не хватает данных.
